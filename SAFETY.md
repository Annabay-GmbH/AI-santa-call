# Child safety and operator runbook

Santa Call is a prototype. These controls are layers, not a guarantee of safety, legal compliance, real-world age, or real-time protection. Do not deploy it to children until qualified specialists have evaluated it and the operator has completed the README launch checklist, consent and privacy arrangements, ZDR setup, and a staffed incident response process. Test with synthetic or consenting adult data only until applicable requirements are met.

## Child disclosure and supervision

The interface explains, in each offered language, that Santa is a pretend AI character, AI may make mistakes, and children should stay with an adult and keep private information and secrets private. An adult is asked to read the disclosure with younger children. The call UI repeats a short privacy reminder. Translations, reading level, accessibility and voice quality still need independent review and testing with families.

## Consent and age limitations

A grown-up must tick the in-app acknowledgement before the server creates a call. The app has no age verification, parent identity check, or independent evidence that the adult is the child's parent or guardian. A checkbox can be submitted by anyone, including a child, and is not necessarily verifiable parental consent. The operator must determine and implement any legally required parental consent and age assurance in each jurisdiction before public use. The app does not prove that a grown-up remains present. `CHILD_SAFETY_REVIEWED=true` is the operator's attestation that the necessary privacy and safety review has been completed; it does not verify consent, legal compliance or ZDR.

## Protected event log

Configure `SAFETY_EVENTS_FILE` as an absolute path to a persistent restricted event file outside the repository. Create it with owner-only permissions before running the monitor, for example `umask 077` and `touch` in a protected directory. The app refuses to start calls or record events if the file is missing from configuration, not writable, not a regular file, or accessible by group/others. A configuration check does not verify that an on-call person is watching it. This sample uses in-memory calls and a single process; multi-instance deployments need appropriate shared state and distributed rate limits.

## Filtering and limits

The audio is transcribed first. The input and generated answer are separately checked using OpenAI Responses inline moderation and a structured classifier instructed to detect sensitive and urgent topics for ages 3–12, including risky disclosures that might not trigger general moderation. Transient errors, including intermittent 403 responses observed in this deployment, are retried at most twice with the same classifier and moderation model; persistent errors still stop the call. The classifier and its result are not used unless both input and output moderation results are present and unflagged. Only an explicit `safe` result passes. Unknown, malformed, overlong or unavailable screening ends the session rather than playing an unchecked answer. Sensitive or urgent input/output ends the call, displays trusted-adult and immediate-danger guidance, and records a category-only safety event. No classifier is reliable in every language, context or transcription; false positives and missed risks are possible. This is not a substitute for professional child-safety evaluation, context-specific filters, trained human oversight, or an emergency response service. Before release, test adversarial and age-appropriate examples across languages, including indirect abuse and prompt injection, with synthetic data; define thresholds, failure rates and review procedures.

## Reporting and escalation

The page offers a report form with fixed categories. It deliberately accepts no free text, contact information or attachments. The endpoint records only a generated event ID, UTC time and event type. For a service failure, automatic events may additionally contain a fixed diagnostic stage and HTTP status, without audio, transcripts, names, session identifiers or error messages. The app cannot contact or identify a child, associate a report with a call, determine their location, investigate a disclosure, or report an incident to authorities. An HTTP 202 means the event was written locally, **not** that someone has read it or can provide help. If someone is in immediate danger, a trusted adult should contact local emergency services; the app is not an emergency service.

For a supervised single-host deployment, run `npm run safety:monitor` in a separate terminal on a host with access to the event file. It prints existing and new events as `URGENT` or `REVIEW`; it does not notify staff, acknowledge events, deduplicate after restart, or ensure the process remains running. Assign a trained operator to monitor it continuously, and establish escalation coverage, response-time targets, handover and backups. Treat `screen_urgent`, `report_immediate_danger`, and `screen_unavailable` as urgent; stop or pause service as appropriate, notify the designated safeguarding lead using approved internal procedures, and follow local incident and reporting obligations. Review other events for trends, false positives and product improvements. Never include transcripts or identifying information in general-purpose incident logs. Preserve and delete events according to an approved retention schedule; the prototype does not automatically delete or rotate the file. Deployments must add access controls, secure durable centralized monitoring, alerting, audit/acknowledgement, and health checks before real use.
